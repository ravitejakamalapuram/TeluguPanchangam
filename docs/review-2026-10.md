(33/33 Drik Panchang fixtures), but those fixtures only cover tithi, nakshatra, sunrise/sunset,

## 1. Formula corrections (Panchang engine)

| # | Pri | Where | Problem | Fix |
|---|---|---|---|---|
| F1 | P0 | `panchang.js` Durmuhurtham block | Sunday, Monday, Tuesday and Friday use the wrong ghatis. Verified: Sunday 2026-10-04 Hyderabad gives 10:29 IST; correct is ~16:30. | Daytime ghati ranges after sunrise (30-ghati day): Sun 26–28; Mon 16–18 and 22–24; Tue 6–8 plus night 12–14 after sunset; Wed 14–16 (ok); Thu 10–12 and 22–24 (ok); Fri 6–8 and **16–18** (code has 17–19); Sat 0–4 (ok). Night ghati = (next sunrise − sunset)/30, not (24h − day)/30. |
| F2 | P0 | `panchang.js` Samvatsara | Year rolls over on 1 March, not at Ugadi. In March `isNewYear` is always true (`monthIndex > 0` holds for Phalguna = 11), and from 1 April it is forced true even if Ugadi is later. Verified: 2026-03-10 shows Parabhava (should be Vishvavasu); 2027-03-10 and 2027-04-03 show Plavanga (should be Parabhava; Ugadi 2027 ≈ 7 April). Sankalpam inherits the wrong year. | Derive the year from the lunar month: in Jan–Apr, if `monthIndex >= 9` (Pushya/Magha/Phalguna) it is still the previous samvatsara; otherwise the new one. Add Drik fixtures for the days either side of Ugadi 2026/2027. |
| F3 | P0 | `panchang.js` `yoga` | Tithi and nakshatra follow the Udaya (sunrise) convention, but the yoga returned is the **midday** sample; karana is also the midday sample. Header can show a yoga that ended before noon. | Compute yoga/karana at `sunriseAstro`, same as tithi/nakshatra. Add yoga to the Drik fixture comparison. |
| F4 | P0 | `newtab.js:454` `checkBirthday` | `new Date(userSettings.dob)` parses `YYYY-MM-DD` as UTC midnight, so for every US-timezone user the birth day is the **previous** date — wrong birth nakshatra/month, wrong birthday banner. Birth time (`tob`) is stored but ignored; birth nakshatra uses the current city, not birth place. | Parse as local: `const [y,m,d] = dob.split('-').map(Number); new Date(y, m-1, d, hh, mm)`, and take nakshatra at the birth instant (`getNakshatraAt`), not Udaya of that day. |
| F5 | P1 | `panchang.js` `amritaOffsets` | Values are one ghati lower than the classical table (Ashwini 42, Bharani 48, Krittika 54 …) and Anuradha is 27 where the table has 34 — a likely typo. | Re-check against Drik Amrit Kalam for a few nakshatras and correct; add Varjyam/Amritakalam to the fixtures. |
| F6 | P1 | `panchang.js` transitions | Transitions are scanned midnight-to-midnight, but the Hindu day runs sunrise-to-sunrise. A tithi/nakshatra ending at 2 AM is shown as "ends tomorrow" with no time, unlike printed panchangams. | Scan sunrise → next sunrise and label times after midnight as "+1". |
| F7 | P1 | `panchang.js` lunar month | Month is taken from the new moon after **midday**; on an Amavasya day after the new-moon instant, the header shows next month while the tithi still says Amavasya. | Use sunrise as the anchor for the month search. |
| F8 | P1 | Varjyam | Only the Udaya nakshatra's Varjyam is computed; when the second nakshatra of the day has its Varjyam inside today it is missed, and a Varjyam that falls on another day is still shown as today's. | Compute for each nakshatra overlapping sunrise→next sunrise; show only windows that intersect the day. |
| F9 | P1 | `newtab.js` `checkForEclipses` | Searches from `panchang.date` (noon), so eclipses peaking before noon are missed; uses the **global** solar eclipse even when it is not visible from the user's city; compares days in the browser zone, not the city zone. | `SearchLocalSolarEclipse(observer)`; for lunar eclipses check the Moon is above the horizon; search from local midnight. |
| F10 | P2 | `panchang.js` Ayanamsa | Linear-plus-quadratic Lahiri approximation, mean (no nutation). Good to ~1 arc-second today, fine for display; drifts slowly. | Optional: use the IAU 2006 precession / Swiss Ephemeris Lahiri definition if sub-minute nakshatra ends are ever compared. |

### Data/text errors

- `panchang.js` nakshatra 12 is `"uttara phalguni / ఉత్తర (Uttara Phalguni)"` — lowercase English in the Telugu slot. Should be `"ఉత్తర ఫల్గుణి / ఉత్తర (Uttara Phalguni)"`. **P0**
- `panchang.js` samvatsara 14 is `"विక్రమ (Vikrama)"` — the first syllable is Devanagari. Should be `"విక్రమ"`. **P0**
- `"ధాత (Dhatu)"` → transliterate as Dhata. **P2**
- Add a smoke test that every Telugu label contains only Telugu-block code points (U+0C00–U+0C7F) plus spaces/slashes, which would have caught both P0 items.

- `package.json`: `main: index.js` doesn't exist, `description`/`author` empty, licence ISC while fonts are OFL — tidy (P2).
- Move `geolocation` to `optional_permissions` and request it on the "Use My Location" click. Removes the "read your location" warning from the install dialog (see 5.1). (P1)

## 5. User adoption plan

### 5.1 Reduce install friction (weeks 1–2)
- Optional `geolocation` (section 3): the install dialog then only shows the new-tab warning.
- **First-run onboarding** (3 screens, in Telugu by default): language → city (US metro list first if the browser timezone is American) → optional DOB for rasi. Today a new user lands on a Hyderabad page with no prompt.
- Explain Chrome's "Change back to Google?" bubble on first open; it is the largest single source of new-tab-extension uninstalls. A one-line note under the clock on day 1 ("Keep this new tab to see today's panchangam") is enough.

### 5.2 Retention (weeks 2–6)
- Weekly-return hooks already exist (festivals, reminders); make them visible: an "Upcoming this week" strip (Ekadashi, Pradosham, Sankashti, festivals) on the main view.
- Ekadashi / Sankashti / Amavasya **lunar reminders** pre-seeded and toggleable (they are the most-searched recurring observances).
- Daily horoscope that actually changes daily (2.P2) — the main reason people come back to a rasi card.

### 5.3 Growth loops (weeks 4–12)
- Share card (4.6) and rating prompt (4.7).
- Ask once (opt-in) for an email address only if a "festival calendar newsletter" is ever wanted — otherwise keep the zero-network promise, which is a selling point; do not add analytics.
- Measure with the data CWS already gives (weekly users, installs/uninstalls by region in the Developer Dashboard) instead of in-app tracking.
